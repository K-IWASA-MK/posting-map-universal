# 桑名の教訓 (Lessons from Kuwana Operations)
## Universal POSTING MAP Quality & Reliability Doctrine — Gate 1

> 本書は、最高位設計契約（`docs/architecture/01_DESIGN_CONTRACT.md` §18, Gate 1 出口基準）に基づき、
> 桑名地区での先行開発および運用において確認された事故・障害・設計課題を整理し、
> Universal POSTING MAP における再発防止原則を規定した公式教訓書である。
> 
> 本書では、**【一次資料・既存証跡から確認できる事故】** と **【設計上の教訓・仮説】** を明確に区別して記録する。

---

## 最上位原則

> **AIが問題を発見したことと、AIに修正権限があることは別である。**
> 
> 発見した不整合・負債・バグを、許可なく「改善」「リファクタリング」と称して修正することは永久に禁止される。
> 予期せぬ状態を発見した場合は即座に作業を停止（STOP）し、MASTERへ報告して承認を得ること。

### 第1条：Identity直列化による起動遅延

- **区分**: 【一次資料・既存証跡から確認できる事故】
- **事故・事象**: Hアプリ起動時に、LIFF SDK初期化 → プロファイル取得 → バックエンドAPI（`getStaffIdentity`）の完了を直列（ウォーターフォール）で待機したため、通信環境の悪い現場で画面が白画面（またはローディング）のまま20〜30秒以上停止し、配布員が操作を開始できなかった。
- **根本原因**: 画面描画（First Paint）がネットワーク越しのIdentity検証APIのレスポンスにブロックされる同期的・直列的なライフサイクル設計。
- **影響範囲**: Hアプリの初期起動速度（LCP）、現場配布員の活動開始体験、ネットワーク寸断時の起動不能。
- **検出方法**: 起動シーケンスのタイムライン計測（`scratch/measure_startup_timeline.mjs` によるPlaywright自動計測）。
- **再発防止ルール**:
  1. **Optimistic First Paint（先行描画）**: ローカルストレージに既存 `staffId` が存在する場合は、Identity APIの完了を待たずにメイン画面を即時先行表示する（`app.js` 1480行目）。
  2. **バックグラウンド非同期検証**: `getStaffIdentity` はバックグラウンドPromiseとして並行実行し、不整合時のみ画面をロックまたは再登録へ誘導する。
- **検証方法**: `tests/test_optimistic_startup_safety.mjs` による起動完了時間とローカルキャッシュ先行表示の検証。

### 第2条：hidden containerでのGoogle Maps初期化

- **区分**: 【一次資料・既存証跡から確認できる事故】
- **事故・事象**: Google Maps の初期化（`initMainMap`）が、DOM要素が `display: none`（または `hidden`）の非表示状態にあるタイミングで実行され、Google Maps API がコンテナサイズを `0px × 0px` と認識して地図が正しく描画されず、画面が灰色（グレーアウト）のままになる事故が発生した。
- **根本原因**: SPA（シングルページアプリケーション）の画面初期化において、DOM表示タイミングと非同期地図スクリプト読み込み完了コールバックの競合（Race Condition）。
- **影響範囲**: Hアプリのマップ画面、配布対象エリアの視覚的確認。
- **検出方法**: `scratch/test_map_race_condition.mjs` による非表示DOM初期化シミュレーション、ブラウザコンソールでの `gm-style` コンテナサイズ確認。
- **再発防止ルール**:
  1. 地図コンテナ（`#main-map`）が可視化され、非ゼロ（Width/Height > 0）のサイズを持つことが確認されるまで `google.maps.Map` のインスタンス化を実行しない。
  2. 画面切り替え（`switchPage`）時に、既存インスタンスが存在する場合は再生成せず `google.maps.event.trigger(map, 'resize')` を実行する。
- **検証方法**: Playwright による実ブラウザテスト（`scripts/test_browser_h_app.mjs`）で `#main-map .gm-style` の実描画（非ゼロサイズ）を検証。

### 第3条：複数Google Maps loader

- **区分**: 【一次資料・既存証跡から確認できる事故】
- **事故・事象**: Hアプリ側と他のモジュール（あるいはページ遷移時）で別々に `maps.googleapis.com/maps/api/js` の `<script>` タグを動的生成・挿入したため、Google Maps API の二重読み込み警告（`You have included the Google Maps JavaScript API multiple times on this page`）が発生し、コールバックが多重発火してメモリリークやクラッシュを引き起こした。
- **根本原因**: 地図APIのローディング責任が分散し、グローバルなロード状態管理（SSOT）が欠如していたこと。
- **影響範囲**: Hアプリ全体の動作安定性、メモリ消費、Google Cloud API クォータの無駄な消費。
- **検出方法**: `app.js` 内の `loadGoogleMapsApi` 周辺コード監査、DOM内の `<script src*="maps.googleapis.com">` タグ数検査。
- **再発防止ルール**:
  1. Google Maps API のローディングは `active/dashboard/app.js` の `loadGoogleMapsApi` を唯一の実行窓口（SSOT）とする。
  2. `window.googleMapsApiLoaded` フラグによる厳格な重複抑止ガードを常時維持する。
  3. Manager Dashboard（管理者画面）は Leaflet を使用し、Google Maps Loader との競合を物理的に遮断する。
- **検証方法**: DOM検査スクリプトによる Maps API script タグの単一性確認（1件のみ存在すること）。

### 第4条：Dashboard/管理思想のHアプリ混入

- **区分**: 【設計上の教訓・アーキテクチャ事故】
- **事故・事象**: 配布員が現場で片手で操作するモバイルHアプリの中に、管理者向けの「全体進捗集計」「他人の活動詳細監視」「名簿管理」「強制割当」などの管理思想・管理UIが混入し、UIが複雑化して現場の操作性を著しく損なった。
- **根本原因**: 「現場活動」と「全体観測」という本質的に異なる2つのユースケースを同一のアプリケーション文脈で扱おうとしたこと。
- **影響範囲**: Hアプリの認知的負荷、現場党員の活動意欲、アプリパフォーマンス。
- **検出方法**: UIコンポーネント監査、`active/dashboard/` 内の機能リストと `01_DESIGN_CONTRACT.md` §3 の対比。
- **再発防止ルール**:
  1. **完全物理分離**: Hアプリ（`active/dashboard/`）は「現場活動（自律的な場所選択・配布記録・チラシ登録・個人ランキング）」のみを担当する。
  2. **Dashboardの独立**: 全体観測・集計・名簿管理は Manager Dashboard（`active/manager/`）に集約し、Hアプリ側には一切持ち込まない。
  3. ノルマ、強制参加、固定担当エリア割当機能の実装を永久に禁止する。
- **検証方法**: `DASHBOARD_QUALITY_GATE.md` Phase 6（Hアプリ非干渉＆アーキテクチャ分離監査）の自動検証。

### 第5条：Offline未考慮

- **区分**: 【一次資料・既存証跡から確認できる事故】
- **事故・事象**: ポスティング現場（地下道、路地、山間部、電波の弱い住宅地）で配布完了登録やGPS写真送信を行った際、オフラインまたは電波断によってリクエストが失敗し、入力した配布枚数や写真データが消失した。
- **根本原因**: すべてのデータ登録が「通信成功」を前提とした同期的な `fetch` / `callApiPost` で直接実行されていたこと。
- **影響範囲**: 配布実績データの欠損、配布員のモチベーション低下、トラブル発生。
- **検出方法**: コミット履歴 `ed9a036 fix(h-app): resolve identity gate scope and enforce verification before enqueueSync`、`active/dashboard/db.js` の差分監査。
- **再発防止ルール**:
  1. 配布登録などのミューテーション操作は、まずローカルの IndexedDB（`PostingMapDB` -> `syncQueue`）に永続保存（`enqueueSync`）する。
  2. 通信可能時にバックグラウンドで自動再送（指数バックオフ: 10s → 30s → 60s → 60s → 60s）を行う。
  3. リクエストごとに暗号学的UUIDによる `requestId`（冪等性キー）を付与し、二重登録をバックエンドで排除する。
- **検証方法**: `active/dashboard/db.js` のユニットテストおよびオフラインシミュレーションテスト。

### 第6条：Mock成功・実機失敗

- **区分**: 【一次資料・既存証跡から確認できる事故】
- **事故・事象**: PCブラウザやNode.jsモック環境ではテストがすべてPASSしていたが、実際のスマートフォン実機（LINE内ブラウザ / LIFF環境）で開くと、CSSレイアウト崩れ、タッチイベント不発、GPSタイムアウト、画像アップロード失敗が発生した。
- **根本原因**: デスクトップブラウザとモバイル実機（特にLINE WebView）における制約（`env(safe-area-inset)`、タッチイベント、メモリ制限、サンドボックス制限）の差異をモックテストで吸収できていなかったこと。
- **影響範囲**: 本番リリース後の即時障害、ユーザーからの不具合報告多発。
- **検出方法**: `scratch/verify_safe_area_modes.mjs`、`scratch/test_browser_h_app.mjs`（Playwright iPhoneエミュレーションによる実機検証スクリプト群）。
- **再発防止ルール**:
  1. モックによるテスト成功は「前提条件」に過ぎず、「リリース完了」の証拠として扱わない。
  2. 画面サイズ（iPhone viewport: 390x844）、User-Agent（LINE WebView）、タッチ動作を含む実機シミュレーションテストを必須ゲートとする。
  3. Definition of Done（完了の定義）に実機動作エビデンスを義務付ける。
- **検証方法**: Playwright を用いたモバイル環境実描画テストの定期実行。

### 第7条：clasp pushのみで本番完了と誤認

- **区分**: 【一次資料・既存証跡から確認できる事故】
- **事故・事象**: `clasp push` を実行してコードをGASにアップロードしただけで「デプロイ完了」と誤認し、Web App の新しいバージョン作成とデプロイ更新（`clasp deploy -i <deploymentId>`）を行わなかったため、本番ユーザーが古いバージョンのコードを使い続け、修正が反映されないトラブルが多発した。
- **根本原因**: GASにおける「スクリプト保存（HEAD）」と「Web App デプロイ（Versioned Deployment）」の二重構造の理解不足。
- **影響範囲**: 本番環境での不具合未修正状態の長期化、デバッグの混乱。
- **検出方法**: `scripts/verify-gas-deployment.mjs` によるデプロイ済みバージョンとローカルコードの整合性検査。
- **再発防止ルール**:
  1. `clasp push` は単なるコード同期であり、デプロイではない。
  2. 本番反映には必ず `deployment.json` に記録された Deployment ID へのバージョン再デプロイ（`scripts/safe-deploy.mjs`）を実施すること。
  3. デプロイ完了後、実際に Web App URL に対して疎通テストを行い、最新コードが返却されることを客観確認する。
- **検証方法**: `npm run verify:gas` による実デプロイ状態の自動検証。

### 第8条：container-bound GAS残存

- **区分**: 【一次資料・既存証跡から確認できる事故】
- **事故・事象**: スプレッドシートに付随していた古いコンテナバウンドGAS（拡張機能 → Apps Script）が残存し、`onOpen` や `onEdit` トリガーが勝手に動作してシート構造を書き換えたり、Standalone GAS API と競合してデータ不整合を引き起こした。さらに、リポジトリ内に `active/dashboard/v2_ui.js`（601行）としてコンテナバウンド用スクリプトが混入し、`.claspignore` でホワイトリスト化されて誤同期されていた。
- **根本原因**: コンテナバウンドGASからStandalone GASへの移行時における旧コード・トリガーの切り離し漏れ。
- **影響範囲**: データベースシートの破壊、APIエラー、二重トリガーによる実行クォータ枯渇。
- **検出方法**: `active/dashboard/v2_ui.js` の現物発見（`SpreadsheetApp.getUi()` を含むコードの残存）。
- **再発防止ルール**:
  1. **Spreadsheet = Pure DB**: スプレッドシート側には一切のスクリプト・トリガー・マクロを含めない（完全コードゼロ）。
  2. **GAS = Standalone only**: すべてのGASコードはスプレッドシートから完全に切り離された単独プロジェクトとして管理する。
  3. コンテナバウンドGASの作成、復元、同期、依存、編集は永久に禁止する。
- **検証方法**: スプレッドシートのバウンドスクリプト不存在確認、リポジトリからの `v2_ui.js` 廃止。

### 第9条：大量ポリゴンによるモバイル負荷

- **区分**: 【一次資料・既存証跡から確認できる事故】
- **事故・事象**: 地区全域の町丁目境界ポリゴン（`boundaries.geojson` 1.0MB以上、数百〜数千ポリゴン）を一度にGoogle Maps上に全数描画しようとしたため、スマートフォンのブラウザがメモリ不足でクラッシュするか、地図のスクロール・ピンチズームが著しくカクつき（FPS低下）操作不能になった。
- **根本原因**: モバイル端末のGPU・メモリ制約を考慮せず、全件ポリゴンを一括レンダリングしたこと。
- **影響範囲**: Hアプリの描画パフォーマンス、端末の発熱・バッテリー消費、ブラウザクラッシュ。
- **検出方法**: `active/dashboard/render.js` 内のポリゴン描画処理監査、低スペックモバイル端末でのFPS低下。
- **再発防止ルール**:
  1. 地図初期表示時は自治体単位または大枠のみを表示し、ズームレベルに応じて必要な町丁目ポリゴンのみを遅延描画する。
  2. ポリゴンデータ自体の簡略化（Simplify: トポロジーを保持した頂点数削減）を事前ビルドで行う。
  3. 不要な非表示エリアのポリゴンはメモリからアンロードする。
- **検証方法**: モバイルエミュレーション環境でのレンダリング時間・メモリ消費量の測定。

### 第10条：Antigravity用のクリーン構造不足

- **区分**: 【一次資料・既存証跡から確認できる事故】
- **事故・事象**: `manager.js`（3,180行）や `app.js`（2,278行）のように単一ファイル内に多種多様な関心事（DOM操作、API通信、状態管理、イベントハンドラ）が混然一体となって長大化していたため、AIエージェント（Antigravity / Flash）がコード変更を行う際にコンテキストを読み誤り、意図しない箇所に副作用やデグレを発生させた。
- **根本原因**: モジュール分割の不足、関心事の分離（Separation of Concerns）の欠如、単一責任の原則の崩壊。
- **影響範囲**: AI開発の生産性低下、バグ混入率の上昇、コード監査の難航。
- **検出方法**: ファイル行数測定（3,000行超ファイルの存在確認）、過去のバグ修正履歴。
- **再発防止ルール**:
  1. ファイルサイズを適切な粒度（目安300〜500行以内）にモジュール分割する。
  2. UI描画（Stateless）、状態管理（State）、通信（API）、データモデル（Model）を明確なディレクトリ階層に分離する。
  3. AIが局所的なコンテキストだけで安全に変更・テストできる構造を維持する。
- **検証方法**: ファイル行数リミット監査およびESLint等の静的解析。

### 第11条：AIによる未依頼変更

- **区分**: 【一次資料・既存証跡から確認できる事故】
- **事故・事象**: AIエージェントが指示されたスコープを超えて、「コードが汚いから」「ついでに共通化できるから」「より最新の書き方に直した」と勝手に判断し、指示されていない関数やファイルを大量に書き換え、既存の動作保証を破壊した。
- **根本原因**: AIの自律性に明確な境界（憲法・就業規則）が与えられていなかったこと。
- **影響範囲**: 既存動作の破壊、監査不能な巨大差分の発生、プロジェクト信用の失墜。
- **検出方法**: `git diff` による事前宣言外変更の検出、過去の指示逸脱記録。
- **再発防止ルール**:
  1. **No Plan → No Proceed → No Implementation**: 計画立案とMASTER承認なしの実装・変更は絶対禁止。
  2. **No Silent Changes**: ファイル変更前に「対象ファイル、関数・行、変更内容、変更理由、変更しない範囲」を日本語で事前宣言する。
  3. **Scope Lock & 最小侵襲**: 指定範囲外のコード不可侵。最小限の行数のみ変更。「ついで」の改善は絶対禁止。
  4. **差分照合必須**: 実装後、必ず `git diff` で事前宣言と実際の変更内容を照合し、宣言外変更が1行でもあれば即時失敗（HARD STOP）とする。
- **検証方法**: `AGENTS.md` の常時ロード、`git diff` 自動監査。

### 第12条：新旧ロジック併存によるZombie Code

- **区分**: 【一次資料・既存証跡から確認できる事故】
- **事故・事象**: 新しい実装を追加した際、古いロジックや使われなくなった関数・ファイル（例: `active/dashboard/v2_ui.js`、`data/area_mapping.json`、未参照の旧エンドポイント）を確実に削除せず「念のため」と残した結果、新旧のロジックが併存し、後続の開発者がどちらが正本か判断できず、古いコードを誤って呼び出す・保守する混乱が生じた。
- **根本原因**: 移行完了時における旧コードの完全撤去（Decommissioning）プロセスの欠如。
- **影響範囲**: アーキテクチャの濁り、保守工数の浪費、誤ったコード修正のリスク。
- **検出方法**: リポジトリ全体のgrep検索、未使用ファイルの現物調査（`v2_ui.js` がHTMLから一切読み込まれていない事実の特定）。
- **再発防止ルール**:
  1. 新ロジックへの移行が完了した旧コードは、即座に安全に完全撤去する。
  2. 「念のためコメントアウト」「使われない関数の放置」を禁止する。
  3. 現行Hアプリ構造台帳（`03_CURRENT_H_APP_INVENTORY.md`）において、全ファイルの生存状態（現役 / 廃止）を明記・追跡する。
- **検証方法**: 未使用コード検出ツール（Dead Code Elimination）および台帳突合。
