# ADR-005: 確定データSSOT・冪等性・実績保護 (SSOT, Idempotency, and Distribution Record Protection)

- **Status**: ADAPTED (ADAPT)
- **Date**: 2026-09-22
- **Deciders**: Universal POSTING MAP Architecture Board
- **Consulted**: `docs/architecture/01_DESIGN_CONTRACT.md` §2, `docs/data/DATA_DICTIONARY.md` §0, §1, §5, `docs/data/DATA_LIFECYCLE.md` §2, `docs/api/API_CONTRACT.md` §4, §17

---

## 1. Context (背景と課題)

外部のアーキテクチャ提案において、「同一 `rowId` が完了状態であれば更新をスキップする」「最新タイムスタンプ勝者（timestamp winner）によって既存レコードを上書きする」という設計案が提示された。
しかし、この設計はポスティング業務の本質を破壊する重大な欠陥を抱えている。

同一の町丁目（同一 `rowId`）であっても、以下のような正当な活動事実が頻繁に発生する：
1. 世帯数が膨大（数千世帯）なため、同一町丁目に複数日・複数回に分けてポスティングを行う。
2. 同一の町丁目を複数の配布員が分担して同時にポスティングを行う。
3. 朝配布したエリアに追加の配布物を夕方に再度配布する。

もし `rowId` を一意キーとして重複判定を行ったり、最新タイムスタンプによる上書き（timestamp winner）を採用した場合、過去に配布員が汗を流して実施した正当な活動実績が不可逆的に消去・上書きされてしまう。

---

## 2. Decision (決定内容)

Universal POSTING MAP では、**「Spreadsheet DB を唯一の正本 (SSOT: Single Source of Truth)」** と定め、正当な配布実績を絶対に消去・上書きしない以下の冪等性・実績保護モデルを確定する。

```text
┌─────────────────────────────────────────────────────────────┐
│ 識別子の厳格な分離                                          │
│   ・rowId     : 地理マスター識別子 (町丁目を示す番号)        │
│   ・requestId : 1回の配布完了操作を識別する UUID v4         │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ Backend (GAS) での受容判定                                  │
│                                                             │
│ 1. 同一 requestId の再送 (通信瞬断・リトライ・連打)         │
│    ──► Idempotent Hit                                       │
│        新規書き込みをスキップし、既存レコード情報を返却     │
│        (HTTP 200, isDuplicate: true)                       │
│                                                             │
│ 2. 異なる requestId の送信                                   │
│    ──► 新規の正当な活動事実として受容                        │
│        たとえ【同一 rowId】であっても拒否・上書きせず        │
│        DistributionRecord シートへ新規行として追記 (Append) │
└─────────────────────────────────────────────────────────────┘
```

### 【絶対不変条件と禁止事項】
1. **Spreadsheet DB の SSOT 性**:
   - 正本データは Google Spreadsheet DB にのみ存在し、端末ローカルの IndexedDB はオフライン送信用キューおよび読み取りキャッシュに過ぎない。
2. **`rowId` による重複判定の絶対禁止**:
   - `rowId` は地理的単位（町丁目）であり、トランザクションの一意識別子ではない。
   - 「同一 `rowId` の実績が既に存在する」という理由で、異なる `requestId` を持つ新規実績の登録を拒絶またはスキップしてはならない。
3. **Timestamp Winner (上書きルール) の採用禁止 (REJECT)**:
   - タイムスタンプ比較によって既存の `DistributionRecord` 行を上書き・更新する方式は完全に禁止する。
   - `DistributionRecord` は追記専用（Append-Only）の不変ログ（Audit Trail）として保持し、過去の実績行を不可逆的に消失させてはならない。
4. **Server Wins の厳格な境界**:
   - 「Server Wins」とは、クライアントの一時的な画面表示状態やオフラインキャッシュとサーバー（Spreadsheet DB）の間でデータ不整合が生じた際、サーバー側に永続化された確定データを正本として優先する原則（API_CONTRACT §17）であり、サーバーが既存実績を上書き消去することを意味しない。
5. **PinStatus と DistributionRecord の分離**:
   - `PinStatus`（現在進行中のピン色・状態）は最新の完了状態を反映して更新（Update）されるが、`DistributionRecord`（完了実績履歴）は常に新規行として追記（Append）される。この 2 つのデータ構造を混同してはならない。

---

## 3. Consequences (影響と効果)

### ポジティブな影響
- 配布員が実際に行った正当なポスティング活動の事実が 1 件たりとも消失・改ざんされず、完全な活動履歴として保全される。
- 通信エラーやリトライに伴う多重計上は `requestId` による厳密な冪等性判定によって防止される。
- 追加配布や複数人による同一町丁目での協調配布がデータモデル上自然にサポートされる。

### ネガティブな影響 / リスクと緩和策
- **重複判定キャッシュの実装**: 現在のバックエンド実装では `requestId` による冪等性検証機構が未実装（GAP）であるため、Gate 5 以降で `CacheService` または専用キャッシュシートを用いた UUID v4 判定ロジックを安全に追加実装する必要がある。
