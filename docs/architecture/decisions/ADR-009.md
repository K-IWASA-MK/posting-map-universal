# ADR-009: 冪等性保証（requestId）・構造化監査ログ・機械的ガバナンスの実装方式 (Implementation Architecture for Idempotency, Structured Logging, and Governance Enforcement - Audited)

- **Status**: ACCEPTED WITH OPEN ASSUMPTIONS (ADOPT)
- **Date**: 2026-09-23
- **Deciders**: Universal POSTING MAP Architecture Board
- **Consulted**: `AGENTS.md`, `docs/architecture/01_DESIGN_CONTRACT.md`, `docs/architecture/decisions/ADR-004.md`, `ADR-005.md`, `ADR-008.md`, `docs/architecture/GATE_6_IMPLEMENTATION_DESIGN.md`

## 1. Context (背景と課題)

Gate 5 Evidence Audit において識別された 4件の実装ギャップ（GAP-01〜04）および 1件の未確定事項（UNDET-01）について、Gate 6 監査指摘に基づき、以下の本質的課題を再定義した：

1. **GAP-01 (Idempotency Authority & Legacy Client)**:
   - 一時的なキャッシュ（`CacheService`）は消失しうるため、真の永続的冪等性の Authority（情報源）にはなり得ない。Durable Storage（スプレッドシート）を基盤とする堅牢な照合が必要である。
   - クライアントから一意識別子（`requestId`）が渡されない旧クライアントに対して、サーバー側で代理 UUID を発番する方式は、再送時に別の UUID となり二重書き込みを論理的に防止できない。
2. **GAP-02 & UNDET-01 (Load Model & GAS Quota)**:
   - 要件書にスループット数値規定が存在しないため、活動員数や req/sec はすべて設計上の仮定（Design Assumption）として扱い、未実証事項を明確に区別する必要がある。
3. **GAP-03 (Structured Logging)**:
   - JSON 出力スキーマを定義するが、GCP Cloud Logging 側での構造化取り込みは現フェーズでは未実証（Unverified at runtime）として扱う。
4. **GAP-04 (Mechanical Governance)**:
   - PreToolUse インターセプターと Git Hook・静的チェックを混同せず、現在利用可能なメカニズムと将来設計を明確に分離する。
5. **Rollback (Data Loss Risk)**:
   - スプレッドシート全体の過去版復元は、障害発生後に登録された他の町丁目の正常実績を不可逆的に巻き戻す重大なデータ消失リスクを孕む。

## 2. Decision (決定内容)

Universal POSTING MAP では、以下の実装アーキテクチャを正式採用する。

```text
┌─────────────────────────────────────────────────────────────┐
│ 1. requestId 冪等性・正当再配布保護モデル                   │
│    ・Durable Authority: スプレッドシート Q列 (永続的SSOT)   │
│    ・Performance Cache: CacheService (一次キャッシュ層)     │
│    ・旧クライアント移行: 冪等性非保証 (Best-Effort) とし、   │
│      新クライアントへの即座移行 (Sunset) を推進             │
│    ・正当再配布: 同一 rowId でも requestId 異なれば新規追記 │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. 構造化監査ログ基盤 (Structured Audit Logging)            │
│    ・新設: StructuredLogger クラス                           │
│    ・出力: JSON 構造化ログ (Cloud Logging 連携設計)         │
│    ・マスキング: lineUserId は subjectHash (SHA-256) 変換   │
│    ・追跡性: traceId = requestId による完全なリクエスト追跡 │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. 負荷検証モデル・段階的ガバナンス・データ保全             │
│    ・負荷モデル: 設計仮定 (Design Assumption) として明示     │
│    ・ガバナンス: 分類 A (リポジトリ内スクリプト/Git Hook) を│
│      先行配備。IDE PreToolUse は将来近代化へ分離            │
│    ・データ復元: スプレッドシート全体復元を原則禁止とし、   │
│      局所修正 (Surgical Repair) を基本原則とする            │
└─────────────────────────────────────────────────────────────┘
```

### 【詳細決定事項】
1. **Durable Storage を Authority とする 2段階照合**:
   - `CacheService` はパフォーマンス最適化のためのキャッシュ層であり、キャッシュ消失後も **スプレッドシート `配布実績YYYY-MM` シート Q列（`requestId`）** から確実に重複を検知・スキップする。
   - 同一町丁目（同一 `rowId`）への別日再配布や複数人協調配布は、異なる `requestId` を持つ正当な活動事実として受容し、常に新規行として追記（Append-Only）する。
2. **旧クライアントに対する移行仕様**:
   - `requestId` のない旧クライアント操作は「真の操作冪等性は非保証（Best-Effort Only）」とし、移行期間中のフィンガープリントによる一時的連打抑止にとどめ、速やかに新クライアント（UUID v4 必須）へ更新させる。
3. **データロールバックの厳格な統制**:
   - スプレッドシート全体の版復元は他の正常実績を消失させるリスクがあるため、原則禁止（局所修正を原則）とし、全体復元は事前 CSV バックアップと MASTER 承認を必須とする独立承認ゲートを設ける。
4. **段階的ガバナンスの適用**:
   - 現環境で利用可能な Git Pre-Commit Hook および静的監査スクリプトを Gate 7 で配備し、未配備の IDE 内部 PreToolUse フックは将来近代化（Gate 8以降）として分離する。

## 3. Consequences (影響と効果)

### ポジティブな影響
- キャッシュ消失時でもスプレッドシート Q列により、過去すべての配布操作に対する二重登録が 100% 確実に防止される。
- 正当な追加配布や再配布が一切スキップ・上書きされず、完全な活動実績が保全される。
- スプレッドシート一括復元による正常実績消失リスクがアーキテクチャ上統制される。

### ネガティブな影響・トレードオフ
- 旧クライアントのままでは通信瞬断時の完全な重複排除が保証されないため、PWA のキャッシュ更新通知を適切に促す運用が必要となる。

## 4. Verification (検証方法)

1. `tests/test_request_id_idempotency.mjs` による単体テスト（同一 `requestId` の重複排除、異なる `requestId` の受容確認、CacheService 消失時の Durable Q列照合確認）。
2. `tests/test_structured_logger.mjs` によるログ JSON スキーマおよびマスキング検証。
3. ステージング環境における実機負荷テスト（シナリオ A〜I）による実測検証。
