# ADR-015: Universal POSTING MAP Performance Contract & SLA Specification

## Status
Accepted

## Context
POSTING MAP は現場のポスティング配布員が日常的に利用するフィールドオペレーションシステムである。
配布員は山間部、集合住宅、地下、移動中などの電波状況が不安定な環境下で頻繁にアプリを開閉し、配布進捗の確認や完了報告を行う。
このような現場環境において、起動の遅延、画面のフリーズ、同期ブロックが発生すると、現場作業そのものが中断・停止する。

最高位設計契約（`docs/architecture/01_DESIGN_CONTRACT.md`）第14節「性能契約」に基づき、Universal POSTING MAP Engine における性能指標、測定境界、SLA（サービスレベル合意）目標値、動的スケーラビリティ原則を恒久的に固定・明文化する。

## Decision

### 1. $T_0 \sim T_5$ 測定境界シーケンスの公式固定
システムの起動から同期完了までのライフサイクルを以下の 6 段階の測定境界として固定する。

```text
  [T0: Navigation Start]
        │
        ▼ (HTMLパース・CSSロード・DOM構築)
  [T1: DOM Ready / 基本UI描画]
        │
        ▼ (Optimistic First Paint: ローカル認証・保存状態の展開、ローディング解除、メインUI可視化)
  [T2: 主要UI展開完了] ─── ★ SLA判定ポイント (Warm ≤ 200ms / Cold ≤ 800ms / Offline ≤ 200ms)
        │
        ▼ (地図コンテナマウント・サイズ確定)
  [T3: 地図コンテナ確定]
        │
        ▼ (Map API初期化・マーカーマウント完了・イベント待機)
  [T4: 地図・ピン操作可能]
        │
        ▼ (Snapshot / Backend API 差分同期完了)
  [T5: 最新差分同期完了]
```

各測定点の定義：
- **$T_0$ (URL / LIFF 起動開始)**: `performance.timing.navigationStart` または実行開始時点（$0\text{ ms}$）。
- **$T_1$ (基本UI描画完了)**: `DOMContentLoaded` 発火時点。スケルトン・ヘッダー骨格の初期描画完了。
- **$T_2$ (主要UI展開完了)**: 後述の「実ユーザー状態」を満たした瞬間。
- **$T_3$ (地図コンテナ確定)**: `#main-map` 要素の DOM サイズ・位置・CSSレイアウト確定時点。
- **$T_4$ (地図・ピン操作可能)**: マップインスタンス初期化完了、初期マーカー描画完了、ユーザーインタラクション待機完了時点。
- **$T_5$ (最新差分同期完了)**: Backend Snapshot または SystemSummary の応答反映が完了し、同期ステータスが更新された時点。

### 2. $T_2$（主要UI展開完了）の実ユーザー状態との対応関係
$T_2$ は単なるコード上の関数呼び出し（`showMainApp()`）の完了ではなく、**配布員（実ユーザー）から見て以下の状態が成立した瞬間**を厳格に指す：
1. **初期ローディング画面（全画面スピナー・進行状況プログレスバー）が完全に解除**されること。
2. **メイン操作画面（ヘッダー、ナビゲーションバー、主要操作カード）が可視化（`opacity: 1`, `display: block`）**されること。
3. 配布員が「アプリが立ち上がり、操作可能な状態になった」と**視認・認識できる状態**に到達していること。

### 3. SLA 統一測定プロトコル & 判定基準
実機ブラウザ・ランタイムにおける性能検証において、以下の統一測定プロトコルを適用する。

- **測定回数**: 各シナリオにつき **独立 5 回測定**（$N=5$）。
- **判定代表値**: **中央値（Median）** を採用。あわせて Min, Max, Mean を記録。
- **PASS 判定条件**:
  1. 代表値（Median） $\le \text{SLA 目標値}$ であること。
  2. 最大値（Max） $\le \text{SLA 目標値} \times 1.25$（許容上限）以内であり、異常スパイク・ハングアップがないこと。

| 測定シナリオ | SLA 目標値 | 測定条件 | PASS 判定条件 (統一基準) |
| :--- | :---: | :--- | :--- |
| **Warm Start ($T_2$)** | **$\le 200\text{ ms}$** | `localStorage` に有効な `user_info` が存在し、キャッシュから即時復元される起動 | 5回測定の中央値 $\le 200\text{ ms}$ かつ 最大値 $\le 250\text{ ms}$ |
| **Cold Start ($T_2$)** | **$\le 800\text{ ms}$** | キャッシュ・Storage なしの初回起動（Identity API 非同期呼び出し中もUIブロッキングなし） | 5回測定の中央値 $\le 800\text{ ms}$ かつ 最大値 $\le 1000\text{ ms}$ |
| **Offline Start ($T_2$)** | **$\le 200\text{ ms}$** | 端末オフライン（`navigator.onLine === false`）状態での起動 | 5回測定の中央値 $\le 200\text{ ms}$ かつ 最大値 $\le 250\text{ ms}$、かつエラー停止なし |

### 4. マーカー性能・再生成スキップ原則
- ピン状態（未配布／配布中／完了）に変更がない場合、マップ再描画や再同期イベント時にも既存マーカーオブジェクトを破棄・再生成せず、再利用する（再生成回数 0 回）。
- 差分が存在する場合のみ、該当ピンのアイコン・プロパティのみを最小侵襲で更新する。

### 5. Universal Engine 動的 $N$ 件スケーラビリティ原則
- 桑名市 337 件は「現在のテストデータ」であり、Universal Engine の固定件数・性能上限として扱わない。
- 地区マスターの件数 $N$ が任意（検証用サンプル: $N=100, 337, 1000$ 等）であっても、パース・初期化処理時間およびメモリ消費量が極端なスパイクや指数的増大を起こさず、実測上、**線形増加傾向**にあることを確認・保証する。

### 6. 非ブロッキング・ネットワークウォーターフォール原則
- 画面表示（$T_2$）を阻害する直列ブロッキング同期通信（同期 API コール、重厚な通信待機）を一切禁止する。
- 認証同期・バックエンド差分同期はバックグラウンド Promise として非同期並行実行し、UI のレスポンスを犠牲にしない。

## Consequences
- 配布員端末における即時操作性（Warm / Offline $\le 200\text{ ms}$）が恒久的に保証される。
- 地区ごとの町丁目規模の違い（数十町丁目〜数千町丁目）に対しても破綻しない高いスケーラビリティを確保する。
- 外部 APM ツール等の過剰設計を排除し、軽量・高速な Universal Engine アーキテクチャが維持される。
